## Access application logs

Open [Render API logs](https://dashboard.render.com/web/srv-dbmj30ijnfac73akcl20/logs).
Sign in to the existing Render account and select Application logs. Choose the
time window, then search for the request identifier or an event/reason code.
Use the actual observed Dashboard labels; platform HTTP access logs and advanced
latency charts can have different plan requirements from application stdout.

To practice correlation without invoking a model:

```sh
curl -i https://rag-study-demo-api-4ae2.onrender.com/health
```

Read x-request-id in the response headers. Search for that value in Render Logs.
The incoming request and request completed events use the same reqId; completion
includes the status and responseTime in milliseconds. This exact correlation was
verified with HTTP 200 during the review. The identifier is generated by the API.

Client elapsed time includes networking and possible service startup/queuing.
The API's responseTime measures its own request lifecycle after admission.
The controlled request showed a substantial difference between those values,
with startup/hibernate messages in the same window. This is useful evidence for
investigation, not an attribution of every millisecond to one cause or a load test.

Logs contain bounded metadata and reason codes. Questions, document contents,
credentials and provider response bodies belong outside operational output.
Successful HTTP events are not a distributed trace tree.

## Access AI metrics and costs

Open [Lumora Usage & costs](https://rag-study-demo-web-4ae2.onrender.com/workspace/usage).
Sign in, select the workspace in the global selector, then open Workspace →
Usage & costs. Access requires owner membership in that workspace.

Choose the reporting period. Expand a model to inspect its recorded cost,
tokens, latency and measurement provenance. The daily view and operation groups
provide other breakdowns; Export metrics downloads the authorized aggregate data.
Workspace billing totals/identity are not copied into this public review.

The inspected UI distinguishes provider-reported and estimated dollars and
explicitly says that its selected historical window covers answers only.
Code also measures newer embedding, reranking and judge operations through the
usage ledger, but those records must actually exist before a window can establish
extended coverage. Do not backfill fictional tokens/costs or label unknown usage
as zero. These are product ledger measurements, separate from LangSmith traces
and Render CPU/RAM measurements, and not a provider invoice.

For infrastructure, open [Render API metrics](https://dashboard.render.com/web/srv-dbmj30ijnfac73akcl20/metrics).
The reviewed Free compute plan restricts application CPU/memory charts. Do not
upgrade a plan merely to complete this inventory. Database infrastructure metrics
belong to the Supabase project; no Supabase operational database query was needed
for this review.

## LangSmith coverage and concrete gap

Open [LangSmith](https://smith.langchain.com/) and sign in to the intended
region/workspace to inspect its existing destinations. This review did not create
an account, project, API key or trace. The default name in application code is
rag-study-mvp; that default is not proof that a corresponding project exists.

The installed integration is an outer workflow decorator. Its answer method
uses traceable with processed input/output summaries. The normal chat route,
however, prefers answerStream, and that decorator delegates answerStream directly
to the inner workflow. The LangGraph retrieval/generation calls also explicitly
suppress nested LangSmith tracing. Consequently, changing the flag alone does
not establish traces of the current streamed chat or a per-stage LangSmith tree.

Pinned source evidence:

- [LangSmith decorator](https://github.com/willianmesko/rag-study-mvp/blob/151ccef257f79882754d64d6c3bf49d234ad84fc/apps/api/src/modules/chat/infrastructure/langsmith/langsmith-tracing-workflow.ts)

## Optional local inspection

The [existing operations guide](observability.md#local-monitoring) explains how
to start the separate local Compose stack and point a local API at it. It was
not started during this review. Once deliberately running with a local API:

| Signal | Local viewer |
| --- | --- |
| Operational dashboard | http://localhost:13030 (Grafana) |
| Distributed traces | http://localhost:16686 (Jaeger) |
| Metrics and alert rules | http://localhost:19090 (Prometheus) |

These loopback addresses are not public Lumora monitoring URLs. The local
API must enable/export OTLP to that collector to produce data. Merely opening
a viewer does not connect it to the Render application.
